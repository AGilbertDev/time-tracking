# The multi-agent pipeline

This project is the proof of concept for how I build software with AI agents. The product is a real translator time tracker, but the repo doubles as a working demonstration of a disciplined, multi-stage pipeline. Every feature is built one at a time, each stage handled by a specialist agent, and the commit and pull-request history is left intact so the process is visible after the fact.

This document is the source of truth for that process. The portfolio project page tells the same story in a shorter form for visitors.

## The flow at a glance

A feature moves through ten steps. Some are mine to decide, some are run by an agent, and one is automation. The design, build, and test steps run inside an isolated devcontainer sandbox so the autonomous work never touches my machine directly.

| Step           | Who             | What happens                                                                                                             |
| -------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1. Intent      | Me              | I decide what to build and describe it in a sentence or two.                                                             |
| 2. Specs       | Agent           | The `specs` agent writes a spec in `docs/specs/`.                                                                        |
| 3. Spec review | Me              | I confirm the spec is right before any code exists.                                                                      |
| 4. Design      | Agent (sandbox) | The `design` agent produces a visual blueprint.                                                                          |
| 5. Build       | Agent (sandbox) | The `frontend` and `backend` agents implement it, with `compliance`, `seo`, and `accessibility` passes where they apply. |
| 6. Tests       | Agent (sandbox) | The `unit-test` agent writes Vitest coverage for the logic.                                                              |
| 7. Test review | Me              | I review the implementation and the test results.                                                                        |
| 8. Commit      | Agent           | The `code-review` agent reviews the diff, then the `commit` agent commits under the AGilbertDev identity.                |
| 9. CI          | Automation      | The CI action runs on the push and reports on the pull request.                                                          |
| 10. PR review  | Me              | I read the pull request and merge.                                                                                       |

The human gates at steps 1, 3, 7, and 10 are the point. The agents do the work, but I stay responsible for intent, correctness, and the final merge.

## The devcontainer sandbox

Steps 4 through 6 are meant to run inside the devcontainer defined in `.devcontainer/`. That is a Node base image with git, Bun, and the Claude Code CLI, so an agent can design, build, and test a feature in isolation without reaching into my working environment. The sandbox is what makes "let the agents build it autonomously" safe rather than reckless.

Status as of the current pass: the flow is documented and the sandbox is installed, but the pipeline is being driven from the main environment for now. Wiring each build stage to actually execute inside the container is a tracked follow-up, not yet done. This section will be updated to past tense once real isolation is in place, so the doc never claims something the repo does not do.

## The agents

Each agent is a plain Markdown definition in `.claude/agents/agilbertdev/`, symlinked from the shared `ai-agents` repository so the same set is reused across all my personal projects. The `pipeline` agent orchestrates the rest.

### pipeline

The front door for all feature work. It routes each stage to the correct specialist, hands off explicitly at every transition, and gates the commit. It never writes code itself. Every feature starts here, one agent per stage, and an incomplete result gets sent back to its agent before the pipeline advances.

### specs

Writes the feature spec to `docs/specs/<feature-name>.md` before any code is written. The spec covers intent, inputs, outputs with acceptance criteria, edge cases, and open questions. It asks at least one clarifying question first and never writes implementation code. This stage is never skipped.

### design

Produces the visual blueprint for a feature: layout regions, component hierarchy, the specific Tailwind classes, responsive behaviour, and motion. It leans on Nuxt UI primitives first and semantic tokens throughout, never raw hex. It writes no `.vue` code. Skipped when a change has no UI.

### frontend

Implements the Nuxt pages, Vue components, and composables from the spec and the design blueprint. All user-facing copy goes through i18n with both French and English added together, colours are semantic tokens, and icon-only controls get an `aria-label`. It never writes server or database code. Skipped for backend-only work.

### backend

Implements Nitro server routes, Drizzle queries, and Zod schemas for Turso. Every input is validated at the boundary before any database call, secrets never reach the client, and handlers stay thin with logic in `server/utils/`. It never touches a `.vue` file. Skipped for pure UI work.

### compliance

Reviews a feature against Québec Law 25, GDPR, PIPEDA, the CASL and CAN-SPAM email rules, Law 101 French-language obligations, and WCAG 2.2 AA. It reports gaps ranked critical, warning, and suggestion, and it does not fix them itself. Skipped only when no personal data, auth, payment, email, or public page is involved.

### seo

Audits and implements on-page SEO: per-page title and description, Open Graph tags with absolute image URLs, JSON-LD structured data, canonical URLs, sitemap, robots.txt, and `hreflang` for the bilingual pages. Skipped for internal or admin pages not exposed to search.

### accessibility

Audits pages and components against WCAG 2.2 AA and fixes the clear, contained issues directly, reporting the architectural ones. Findings carry a file, a line, the WCAG criterion, and a severity. Icon-only controls without a label and a removed focus indicator are treated as critical. Skipped for internal-only surfaces.

### unit-test

Writes Vitest tests targeting 80 percent branch coverage for pure functions, server utilities, and composable logic. Tests sit next to the code they cover. It never mocks a pure function and never writes a test that only passes because the meaningful parts are mocked away. Skipped when a change has no logic worth testing in isolation.

### code-review

Reviews the diff for correctness, security, convention adherence, and quality before every commit. It reports findings with a file, a line, and a severity, and it never edits code during the review. Anything that could leak a secret or user data is critical. This stage is never skipped.

### commit

Commits, and pushes or opens a pull request only when asked. It verifies the git identity is AGilbertDev and runs the relevant tests first, and it refuses to commit if a test fails. It stages files by name, never with `git add -A`, and never skips hooks or force-pushes without being told to. The identity check is never skipped.

## One feature at a time

The discipline is the demonstration. A feature goes all the way from spec to merged pull request before the next one starts, so each entry in the history is a complete, reviewed unit of work rather than a pile of half-finished branches. Specs and code review are never skipped, and a failing test blocks the commit with no bypass.

### Feature 2 — Persist user preferences

### Feature 7 — Avatar upload and private storage

Delivering the avatar upload that Feature 6 deliberately deferred, and delivering it private and authenticated from the start. A signed-in user can choose a photo, preview it locally, save it, replace it, or remove it back to the initials circle, and the stored image then renders in the header trigger, the header account popover, and the profile page. The image bytes never live behind a directly loadable public URL. The core decision is a single storage-driver util (`server/utils/avatarStorage.ts`) that is the only module allowed to touch a storage backend for avatars: it exposes `put`, `get`, and `del` keyed only by `userId`, selects a local filesystem driver under `nuxt dev` and a private Vercel Blob driver (`access: 'private'`, `useCache: false` reads) in production, single-sources that selection so production can never silently fall back to the filesystem, and fails closed with `avatar_storage_unconfigured` when the blob token is missing. ### Feature 16 — The task write API

The first write path the application has ever had. Every task row in existence before this came from the dev seed, so the table had a reader and no writer at all, and `PLAN-01` deliberately left almost every column nullable with `category` and `status` as free text on the reasoning that validation belongs at the write boundary. This feature is that boundary, which makes what it accepts what the database will hold forever. Three routes, `POST /api/tasks`, `PATCH /api/tasks/[id]`, and `DELETE /api/tasks/[id]`, delegate to `create`, `update`, and `remove` handlers over a shared `write.ts` holding the column mapping and the status cross-check, and a shared `projection.ts` that now owns the select list, the overdue `CASE WHEN`, and the row mapper so the overdue rule exists once rather than being copied by the write path. Extracting it shrank the list handler to 38 lines. Only `date` and `category` are required, because they are the only columns that are `NOT NULL` without a default. Both bodies are `.strict()`, so sending `userId` is a 422 rather than a silent drop, and `userId` is set from the session after the spread so no mapped value can shadow it. A foreign row returns 404 rather than the 403 the roadmap's `AC1` named, because 403 confirms the id exists and hands out an enumeration oracle, and the ordering matters as much as the code: the ownership-scoped select 404s before the status check can emit a 422, so the choice of error cannot distinguish someone else's row from no row. Three decisions went the way that stores less rather than more. `estimated_minutes` is stored verbatim and derived nowhere, because deriving it needs the per-category quota `PLAN-32b` has not built and the only quota available today is the 450 default the planning overview already calls wrong, and a wrong frozen estimate is unrecoverable where a missing one is backfillable. `actual_minutes` is never auto-filled from the estimate, so it stays NULL until the user sets it and `effectiveDuration` resolves the fallback at read time, which keeps a duration the user confirmed distinguishable from one the app assumed. And `words_done` gets no writer at all. Spec at [docs/specs/planning/task-write-api.md](specs/planning/task-write-api.md).

The `words_done` decision is the one worth recording in full, because the tempting answer was wrong on evidence rather than on taste. The planning overview contains a line reading that for an ordinary task the app "should set it rather than ask twice", which reads as an instruction to mirror `project_word_count` into `words_done` server-side. That was rejected on three findings. Nothing reads the column for a statistic, since a search across `app/`, `shared/`, `server/`, and `test/` returns only type declarations, a read passthrough, and a display, and there is no quota engine because `PLAN-22` is not built and lands after `PLAN-33` deletes the column. Mirroring is also the same defect as auto-filling `actual_minutes` wearing a different name, storing an assumed value in a column meant for a supplied one. And it is actively wrong on screen, because the task row prints words done over the project total, so a mirrored new task would render `12 000 / 12 000` and read as finished before being started, which is the exact misreading that row's own comment says it was built to prevent. The cost of not writing it is named rather than buried: until `PLAN-33` lands, a user-created task renders `— / 12 000`, which is the `-- /` the owner asked to have removed, so the recommendation carried out of this feature is that `PLAN-33` should land before `PLAN-10` rather than merely early. Two other things came out of the build. `sendZodError` learned to map `unrecognized_keys` issues by key name, because Zod reports every unknown key in a single issue carrying an empty path and the old path-keyed loop discarded it, so a strict-mode 422 would have arrived with an empty `data` and nothing for a client to name. And the `PRAGMA foreign_keys` question that Feature 8 explicitly deferred to this feature is closed by measurement rather than another comment: a read-only probe with a positive control returned 1, so enforcement comes from Turso's server default and no client configuration is needed. That was recorded in `schema.ts` with its limits stated, that production was not checked and that the in-memory test harness does not issue the pragma, so the suite cannot catch a regression there.

Stages run: specs, backend, compliance, unit tests, code review, commit. Design, frontend, SEO, and accessibility were all skipped as genuine non-applications for a server-only feature that ships no markup, and `PLAN-10` and `PLAN-11` own the interface in their own runs. Compliance was deliberately not skipped, because this is the first code path that will ever create real user data rather than seed rows, and it passed with no security or privacy blocker after confirming ownership sits in the `WHERE` clause at all five call sites rather than in an application-level check a refactor could drop, that no request body is spread into an insert, and that the 404 ordering holds. It left two notes for later features, that error responses echo submitted key names so a client must never render the raw `statusMessage`, and that a deleted task cannot be restored in place since re-creating yields a new id, which `PLAN-34`'s timer must not assume. Verification: 1043 tests across 25 files with ESLint and Prettier clean, and the typechecker reported 46 errors all of one pre-existing class that already hits untouched files, confirmed as pre-existing by injecting a deliberate type error into a new file, watching it get reported, and restoring. Every stage ran through an agent and no implementation code was hand-written, so this is agent-driven, but it is recorded as not fully sandboxed and the reason is orchestration failure rather than scope creep. The orchestrator was declared dead after 181 seconds of transcript silence when it was in fact alive, its children still working, so a second pipeline was started alongside it and two pipelines ran against the same working tree for most of the feature. The collision was caught by a unit-test agent whose `Write` was refused because the file had appeared underneath it, and which correctly stopped and reported rather than overwrite live work. The orchestrator's own code review stage was then killed mid-flight to stop an agent nobody could see from committing a tree that had a failing test in it, and a replacement review found that the failing test had already been fixed by the agent that was killed. One collision artifact survived into the diff and was found by that review, a test fixture still carrying the rejected empty-patch predicate together with the production message under a comment claiming it was what the criterion needed, which is exactly the kind of residue two pipelines leave. Spec at [docs/specs/planning/other-category.md](specs/planning/other-category.md), design at [docs/specs/planning/other-category-design.md](specs/planning/other-category-design.md). The reasoning is written up in the Feature 17 entry above rather than repeated here, because the two were built together in one branch.

**It has its own entry because it has its own spec, and it shares Feature 17's pull request because the one-feature-at-a-time rule was broken.** Splitting the ledger row was the owner's decision once the break was named. One row reading "the inline task editor, and a tenth category" would have hidden a feature's worth of work inside another feature's row, which makes the coverage figures flatter than the work deserves. Two rows against one pull request is the honest shape, and the entry says why rather than leaving a reader to notice that two rows link the same number.

The substantive thing this feature contributed beyond a new id is that it split one flag into two. `trackable` had been answering two questions at once, whether a row's words reach the quota and whether the row is work that can be in progress, and every category before this one answered both the same way. `other` is the first where they differ, because it produces no words and is absolutely a task a user wants to mark finished. So the contract now declares `trackable` and `deliverable` separately, the two helpers fail in opposite directions on purpose, closed on the quota question so a stray id cannot inflate a number and open on the status question so a stray id cannot hide a status the user stored, and a comment covering both together records the principle rather than one note on each that reads as an inconsistency.

Stages run: specs, design, backend, frontend, compliance, accessibility, unit tests, code review, commit. It got its own specs and design stages, which produced the two documents linked above rather than sections inside Feature 17's, and the remaining stages ran once across the shared branch and covered both features in the same pass. SEO was skipped for the same reason as Feature 17, that no new page and no public search surface ships and the planning week is behind authentication and already `noindex, nofollow`. Compliance ran and found nothing of its own: a tenth category id is neither personal data nor a new collection, it sends no email, and the French and English labels were checked against the Law 101 obligation the whole interface already meets.

Verification specific to this feature, rather than the shared branch figure. `test/shared/categories.test.ts` passes 247 tests at exit 0, and 42 of its assertions name `deliverable` or `isDeliverableCategory` directly, which is the split this feature contributed and the part most worth pinning down. The cases that matter are the ones where the two flags disagree, so `other` is asserted `trackable: false` with `deliverable: true`, the four genuinely non-deliverable ids are asserted false on both, and the two helpers are asserted to fail in opposite directions on an unknown id, closed on the quota question and open on the status question. Coercion of a retired id such as `revision` to `other` is covered, as is the resolved `deliverable` boolean reaching `PlanningTask`. What is not verified is the same gap Feature 17 records and for the same reason: nobody signed in, so the `Autre` option in the real category selector, its separator, and its colour at hue 90 were all read statically rather than seen on screen. The colour in particular is a derived candidate the owner still has to confirm against a real display.

### Feature 19 — Per-category quotas

A words-per-hour quota per category, owned by the user and effective-dated, replacing the single global `settings.quota_wph`. A quota belongs to a kind of work rather than to the person doing it, so one number per user could never describe four kinds of work at once, which makes the old setting wrong in shape rather than wrong in value. Spec at [docs/specs/planning/per-category-quotas.md](specs/planning/per-category-quotas.md), design at [docs/specs/planning/per-category-quotas-design.md](specs/planning/per-category-quotas-design.md).

The shape was decided before the build and it exists to accept growth. `category_quotas` is keyed by a free-text `category_id` with no foreign key to any category record, because there is no per-user category record to point at yet and building one is `PLAN-30`. That means the table already accepts an id nobody has invented, so a user-created category will be an insert rather than a migration. The cost of that seam is stated rather than hidden: referential integrity lives in code instead of in the schema, and the protection is that the read path asks about one category at a time and coercion fails closed, so an orphan row never reaches a number. The four shipped figures live on the category descriptors, declared explicitly on all ten with `null` on the six non-trackable ones, so "has no quota" stays distinct from "has a quota of zero".

Nothing is ever deleted or updated in place. The quota is effective-dated in the SCD Type 2 shape `work_schedule` already uses, so editing a figure can never restate a period that has already been reported, and a new figure is a new row. Two migrations rather than one, because the migration ledger is keyed on filename with no checksum and a single file could leave the table created and unrecorded with no way to resume.

**Owner feedback arrived mid-run and changed the standing of the design rather than the design.** The rule that any list must be customizable, modular and extensible was stated after the shape was agreed, and the shape already satisfied it, so the spec gained a section mapping seven choices to the part of the rule each one answers rather than any change to the schema. A second question the same feedback opened, whether the category set itself becomes per-user rows in this feature, was put to the owner four times and never answered. The build proceeded on the orchestrator's stated assumption that `PLAN-30` stays next, recorded in the spec as an assumption attributed to the coordinator with the date and the reversal cost, kept beside the owner's unanswered open question rather than merged into it. That distinction is the point: what the owner decided and what was assumed on his behalf are different things, and the second should be easy to overturn.

Stages run: specs, design, backend, frontend, compliance, accessibility, unit tests, code review, commit. SEO was skipped because every page this touches is authenticated, so there is no public surface to optimise. Specs amended itself four times, three for provenance and citation and one substantive, correcting an acceptance criterion that asked for both the unit hint and the default marker without noticing they wanted the same slot.

Review found no critical issues and two warnings, both fixed rather than shipped. The first is the one worth recording, because it looked like working code. The settings page sent every row on save rather than only the changed ones, which would have written a stored row for all four categories on the first save, erased the default badge from categories nobody touched, filled the effective-dated history with edits that were not edits, and pinned a user to a shipped default forever so improving it could never reach them. The second is that the criterion forbidding `app/` from computing a quota had no guard test, so the property held while nothing defended it.

Five fixes ride along, each because this feature touched the code carrying it: an onboarding field whose two inputs shared one generated id and left the second without an accessible name, a purge comment claiming four deletes where the endpoint issues seven, a seed assertion propped up by a filter that narrows nothing, an override that could have returned a zero divisor, and a source scanner extracted to a shared helper rather than copied.

Verification is worth reading for method rather than for the numbers. Tests went from 32 files and 1576 to 37 and 1837, and the eight cases that disappeared are itemised to a schema field that no longer exists rather than accepted as noise. Every new guard was proved load-bearing by deliberate breakage and restored byte-identical by hash: removing the trackable gate handed a meeting a quota of 900, removing the effective-date filter let a future row restate a past period, downgrading the upsert broke same-day saves, removing the explicit purge delete left a purged row behind, and a probe file importing the resolver into `app/` failed four guard cases by name before being deleted. The unique index is tested with raw SQL and a fresh id rather than through the seed helper, because a second insert through the helper would collide on the primary key and pass whether or not the index existed.

**What this feature is not is verified end to end, and that is the honest headline rather than a footnote.** Neither migration has been applied and there were no database credentials in the environment, so the page has never been loaded against real data. Every rendered-output claim comes from an isolated SSR harness, with no real screen reader, no browser-measured contrast, and no reflow check at 200 percent zoom. The production figure the dropped column held was never read out either, so `AC5`'s record is a labelled gap in the pull request body rather than a number.

**Four orchestration failures belong here, because a trail that records only what went right teaches nothing.** The orchestrator was wrongly declared dead after 73 minutes of flat transcripts and duplicate backend and design agents were spawned against the same working tree; the agents had been parked and resumed on the first probe, and both duplicates were killed before writing a file, so the collision cost nothing but was the same mistake Feature 16 already recorded. Accessibility's completion report sat unrelayed while the orchestrator answered other questions, stalling code review on inattention rather than on work. The orchestrator itself then died before the commit stage staged anything, and the commit, the pull request, this entry and the ledger row were all made by hand.

**And one class of failure appeared four times in four costumes, which is the most useful thing this run produced.** A `sed` and its verifying `grep` were both anchored at column one, so a fix matched nothing and the check confirmed it. A `|| echo` fallback printed a clean result underneath an error. `bun run test | tail` returns `tail`'s exit status, so a piped gate check converts a failure into a pass. And a green suite collecting 174 fewer tests looks exactly like success. Each is a check that cannot fail, and the defence in every case was the same: prove the instrument can report a positive before trusting its negative. That is what turned the `AC3` grep, the purge delete, and the `app/` guard from assertions into findings.

Classified agent-driven with no hand-written implementation code, and not fully sandboxed. Every line of implementation came from a specialist agent and the orchestrator wrote none of it, which holds the first. The second fails on four counts: the run was driven from the main environment rather than the devcontainer, the duplicate-agent collision was self-inflicted, the relay failure stalled a stage, and the commit and pull request were made by hand after the orchestrator died.
